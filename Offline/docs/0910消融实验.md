# HiveMem 5+2 图扩展消融实验（0910）

## 1. 实验目标

在 MemGallery、H2HMEM 和 WorldMemArena（WMA）三个 benchmark 的完整 test split 上，验证 HiveMem 检索配置中“5 个向量召回 + 2 个图扩展结果”里的 2 条图扩展记忆是否有效。

本实验只做 QA test 消融，不重新训练 PPO，不重建 memory bank、query embedding 或 VP。每个 benchmark 固定使用同一个已训练 PPO checkpoint 和 deterministic evidence policy；四种设置之间唯一允许变化的是检索候选的产生方式。

### 1.1 具体运行范围

本实验明确只运行以下三个 benchmark 的 **test split**；不运行 train split，不运行 validation split，也不进行 PPO 参数更新：

| Benchmark | 数据目录 | Test 组成 | Conversation/sample 数 | QA 数 |
|---|---|---|---:|---:|
| MemGallery | `/data/haozhen/Memory-clean/Mem-Gallery/benchmark/data` | 4 个 test conversation | 4 | 275 |
| H2HMEM | `/data/haozhen/Memory-clean/H2HMEM-main/dataset` | Dyadic test + Multi-party test | 4 + 1 | 327 + 33 = 360 |
| WorldMemArena | `/data/haozhen/Memory-clean/WorldMemArena/WorldMemArena/lifelong` | Lifelong test | 8 | 440 |

具体 test conversation/sample 如下，唯一权威来源是 `Offline/configs/multimodal_split_manifest.json`：

- MemGallery（共 275 QA）：
  - `Dog_Behavior_Research_Academic_Life`：61 QA
  - `Entrepreneurship_Blockchain_Economics_Logistics_Nature`：78 QA
  - `Fashion_Personal_Care_Lifestyle_Shopping`：52 QA
  - `Global_Travel_Cultural_Sightseeing`：84 QA
- H2HMEM Dyadic（共 327 QA）：
  - `dialogue10`：75 QA
  - `dialogue11`：81 QA
  - `dialogue7`：78 QA
  - `dialogue9`：93 QA
- H2HMEM Multi-party（共 33 QA）：
  - `dialogue3`：33 QA
- WorldMemArena Lifelong（共 440 QA，每个 sample 55 QA）：
  - `academic_03`
  - `education_03`
  - `finance_01`
  - `health_03`
  - `personal_07`
  - `personal_20`
  - `software_03`
  - `startup_01`

WMA 的 440 QA 包含 11 个题型各 40 题，其中包括 40 条 MB；`excluded_categories` 必须为空。运行前必须用 manifest question ID 重新核对上述清单，不能使用某个旧 config 内可能过期的内嵌 split 列表替代 manifest。

预注册的判断问题：

1. `Top5+Graph2` 是否优于 `Top5`：增加 2 条图扩展结果是否带来收益。
2. `Top5+Graph2` 是否优于 `Top7`：图扩展是否比继续取两条低排名向量结果更有效。
3. `Top5+Graph2` 是否优于 `Top5+Random2`：收益是否来自图结构，而非单纯增加两条上下文。
4. 上述收益是否值得额外的 QA token、cost 和 latency。

## 2. 实验组

| 组名 | 向量召回 | 追加结果 | 总候选上限 | 重复次数 |
|---|---:|---|---:|---:|
| `top5` | Top-5 | 无 | 5 | 1 |
| `top7` | Top-7 | 无 | 7 | 1 |
| `top5_random2` | Top-5 | 随机 2 条 | 7 | 3（seed 42/43/44） |
| `top5_graph2` | Top-5 | 图扩展 2 条 | 7 | 1 |

每个 benchmark 共 6 个正式任务，三个 benchmark 共 18 个任务。`top5_graph2` 也必须在本批次重新运行；旧结果只用于交叉检查，不能直接和本批次新结果拼表，以免 prompt、checkpoint、模型服务或统计版本不同造成混杂。

### 2.1 `top5`

- 使用纯向量索引，`top_k=5`。
- `graph_options=false`。
- 不补足到 7 条。

### 2.2 `top7`

- 使用纯向量索引，`top_k=7`。
- `graph_options=false`。
- 同一道题的前 5 条必须与 `top5` 完全一致；否则视为检索实现或缓存不一致。

### 2.3 `top5_random2`

- 先得到与 `top5` 完全相同的向量 Top-5。
- 再从该题当前可见的同一 memory bank 中均匀、无放回地抽取 2 条。
- 随机候选必须排除 Top-5 memory ID、重复 memory ID、被 benchmark 过滤规则排除的记录及当前 checkpoint 不可见的未来记录。
- WMA 必须继续遵守 prefix visibility，绝不能从未来 session 抽样。
- 每题使用与执行顺序无关的确定性随机种子：`SHA256(global_seed, benchmark, manifest_question_id)`。这样断点续跑、并发数和任务分片变化不会改变随机结果。
- 三个全局 seed 固定为 42、43、44；必须保存每题抽中的 memory ID、来源 session、rank 和 seed。
- 若合法候选不足 2 条，记录为结构性错误并停止该组验收；不得从 Top-5 重复填充，也不得静默减少候选数。

### 2.4 `top5_graph2`

- 使用当前 HiveMem 默认图扩展逻辑：向量 Top-5 后以 `append` 模式追加最多 2 条图候选。
- 图配置固定如下，不得在 benchmark 之间改变：

```json
{
  "seed_k": 0,
  "mode": "append",
  "append_k": 2,
  "expansion_bonus": 0.2,
  "expand_temporal": true,
  "expand_related": true,
  "expand_entity": true,
  "expand_attribute": true,
  "df_max": 0.3,
  "df_stop": 0.5,
  "min_shared": 2,
  "degree_cap": 10
}
```

- 若图中确实没有合法扩展候选，保留实际返回数量并在 trace 中记录原因，不允许用随机项或额外向量项补齐。

## 3. 固定协议

以下设置参考 `Offline/docs/baselines.md` 和 `Offline/configs/test_baseline_matrix.json`，四组实验必须完全一致：

- Split manifest：`Offline/configs/multimodal_split_manifest.json`
- MemGallery test：275 QA
- H2HMEM test：360 QA
- WMA lifelong test：440 QA，`excluded_categories=[]`，必须包含全部 40 条 MB
- 回答模型：`Qwen/Qwen3-VL-4B-Instruct`
- 回答温度：0.0
- 最大输出：512 tokens
- 请求超时：180 秒
- 请求重试：2 次
- Embedding：`Qwen/Qwen3-VL-Embedding-2B`，维度 2048，复用已有 query embedding
- Evidence order：`summary, dialogue, caption, image, vp`
- VP：`qwen3vl4b_all_v1`，启用 strict coverage，每张图最多 5 条 VP
- Graph mode：仅 `top5_graph2` 使用 `append`
- PPO strategy：加载冻结 checkpoint，`deterministic=true`，不得改用 FULL、SUMMARY、随机 evidence strategy 或重新训练 policy
- Prompt：使用运行时当前已验收的官方 benchmark prompt；启动前冻结 `prompt_version`、`prompt_source` 和 `prompt_sha256`
- Evidence context 只允许拼接一次，答案必须按各 benchmark 当前解析器提取后再计算指标
- LLM Judge：OpenRouter `openai/gpt-4o-mini`
- Efficiency profile：`Offline/configs/model_efficiency.json`
- 禁止复用旧 QA rollout cache；四组都必须产生新的回答请求、raw response、解析答案和调用追踪

### 3.1 固定 PPO checkpoint

本批次默认冻结以下 checkpoint，四组之间不得更换：

| Benchmark | Checkpoint |
|---|---|
| MemGallery | `/data/haozhen/Memory-clean/Offline/outputs/PPO/MemGallery_0907PPO_a/checkpoints/epoch_005.pt` |
| H2HMEM | `/data/haozhen/Memory-clean/Offline/outputs/PPO/H2HMEM_0907PPO_b/checkpoints/epoch_005.pt` |
| WMA | `/data/haozhen/Memory-clean/Offline/outputs/PPO/WMA_0909PPO_a/checkpoints/epoch_005.pt` |

选择其他 checkpoint 必须在正式启动前修改本文并重新冻结，不能在部分实验完成后替换。H2HMEM 本批次使用 caption 已回填的 memory bank；由于这可能不同于旧 5+2 结果的 bank 状态，所以必须重跑本批次 `top5_graph2`。

## 4. GPU 与执行调度

配置尽量与 baseline matrix 保持一致：

| Benchmark | GPU | vLLM 端点 | 任务顺序 |
|---|---:|---|---|
| MemGallery | GPU 3 | `http://127.0.0.1:8013/v1` | top5 → top7 → random42 → random43 → random44 → graph2 |
| H2HMEM | GPU 4 | `http://127.0.0.1:8014/v1` | top5 → top7 → random42 → random43 → random44 → graph2 |
| WMA | GPU 5 | `http://127.0.0.1:8015/v1` | top5 → top7 → random42 → random43 → random44 → graph2 |

三个 benchmark 并行，各 benchmark 内部串行，避免同一 endpoint 上不同实验争抢资源。任务统一放入 tmux，支持关闭本地终端后继续运行；每 30 分钟检查进程、GPU、endpoint、已完成 QA、错误数和磁盘空间。

## 5. 实现设计

当前 `Offline/src/evidence_policy/retrieval.py` 对 PPO 检索硬性限制为 `top_k=5` 且 `append_k=2`。正式运行前需做小范围、可复用的配置化修改：

1. 在 `Offline/src/evidence_policy/retrieval.py` 中把候选生成统一为 `vector`、`random_append`、`graph_append` 三种 mode。
2. `vector` 接受 `top_k=5` 或 `top_k=7`；`random_append` 固定 `vector_k=5, append_k=2`；`graph_append` 保持当前 `vector_k=5, append_k=2` 及全部图参数不变。
3. 在 `Offline/scripts/evidence_policy.py` 的三个 benchmark episode builder 中统一调用候选生成接口，不复制三套随机逻辑。
4. retrieval signature 必须包含 mode、vector_k、append_k、graph options、global seed 和可见前缀 signature，防止不同实验错误复用缓存。
5. 每条 rollout 记录 `retrieval_mode`、`vector_k`、`append_k_requested`、`append_k_actual`、`retrieval_seed`、Top-5 IDs、追加 IDs、最终有序 IDs及各项 `via`。
6. policy action 由同一 checkpoint、同一 query embedding 确定；不得因为某组候选较少而改变 evidence threshold 或强制打开 evidence level。

必须新增或扩展现有测试，至少覆盖：

- `top5` 是 `top7` 的严格前缀。
- 三个随机 seed 可复现，且随机项不与 Top-5 重复。
- 改变并发、重试或题目遍历顺序不改变同题随机结果。
- WMA 随机项和图扩展项均无未来 session 泄漏。
- `top5_graph2` 的结果与修改前默认 5+2 实现一致。
- 四种 mode 的 signature 不同，不能交叉命中 rollout cache。
- 每组 prompt hash、checkpoint hash、question ID 集合和 PPO action 一致。

## 8. 指标口径

所有实验结果统一按以下字段及顺序汇总，不增删或改名：

| Baseline | F1 | EM | Judge | Cost-MB | Cost-QA | Lat-MB | Lat-QA | #Calls (MB+QA) |
|---|---:|---:|---:|---:|---:|---:|---:|---:|

- `Baseline` 使用 `<Benchmark> / HiveMem-<组名>`。
- `Cost-MB`、`Lat-MB`：memory 构建阶段指标。本实验复用相同 bank，因此同一 benchmark 的四组应完全相同；仍需从原始构建 trace 合并，不能填 0。
- `Cost-QA`：检索及回答阶段 token 成本，使用 `model_efficiency.json` 的价格并按统一 baseline sample 口径汇总。
- `Lat-QA`：检索及回答阶段模型化延迟。按现行约定除以完整 QA 数，即 MemGallery 275、H2HMEM 360、WMA 440；不得除以 benchmark session/sample 数。
- `#Calls (MB+QA)`：严格沿用 baseline 口径，按 `(MB calls + answer calls) / sample 数`；retrieval calls 单独保存在调用追踪中，不计入该列。
- Judge 调用不计入 Cost、Latency 和 `#Calls (MB+QA)`。
- 所有表格数值保留 6 位小数，并在 `efficiency_metrics.json` 保留原始 token、call、image 数和完整计算公式。

效率参数读取自 `Offline/configs/model_efficiency.json`：

```text
输入价格：$0.05 / 1M tokens
输出价格：$0.25 / 1M tokens
模型化延迟：calls×0.332 + input_tokens×0.000003 + output_tokens×0.00664 + images×0.15
```

## 9. 统计分析

1. `top5_random2` 先对 seed 42/43/44 分别报告完整指标，再报告均值和标准差。
2. 主结果同时报告相对 `top5` 的绝对差值：`ΔF1`、`ΔEM`、`ΔJudge`、`ΔCost-QA`、`ΔLat-QA`。
3. 对逐题 F1、EM 和 Judge 做 paired bootstrap（按 question ID 配对，10,000 次重采样），给出 95% confidence interval。
4. `top5_graph2` 对三个 random seed 分别比较，并额外对 random 三次均值比较；不能只挑最差的随机 seed。
5. 若 `top5_graph2` 相对 `top5` 没有正增益，不能声称“2 有用”；若只优于 random2、但不优于 top7，只能说明图扩展优于随机噪声，不能说明它优于普通向量扩容。
6. 同时报告每增加 $0.001 Cost-QA 和每增加 1 秒 Lat-QA 带来的 F1/Judge 变化，展示质量—成本权衡。
