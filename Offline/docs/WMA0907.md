# WMA Chunk 对照实验计划

## 1.目标

在单张 GPU 5 上完成 WorldMemArena lifelong 的两组 HiveMem 全量实验，对比原有“一轮 user + assistant 一个 chunk”和新的“约 512 tokens 动态组合完整轮次”两种切分方式对建库、检索及回答效果的影响。

两组实验严格顺序执行：先运行原有 round chunk，再运行 512-balanced chunk。除 chunk 输入及独立输出目录外，其余配置保持一致。

## 2.固定配置

- Benchmark：WorldMemArena lifelong，38 个 sample、2,090 QA
- 原有 round chunk：`data/wma_qwen3_vl_embedding_2b/chunks_lifelong.jsonl`，15,437 chunks，平均约 316 tokens
- 512-balanced chunk：`data/wma_qwen3_vl_embedding_2b/chunks_lifelong_512_balanced.jsonl`，8,370 chunks，平均约 506 tokens；完整轮次组合，目标 512 tokens，最大 798 tokens
- 回答与建库模型：`Qwen/Qwen3-VL-4B-Instruct`
- vLLM：GPU 5，端口 8015，单卡 tensor parallel；已有兼容服务时直接复用
- Embedding：`Qwen/Qwen3-VL-Embedding-2B`，端口 8001，维度 2048
- Query embedding：两组共用 `data/wma_qwen3_vl_embedding_2b/query_embeddings_lifelong`
- 建库视觉输入：`image`；向建库 LLM 发送原图，不发送 chunk 中的 image caption
- 建库并发：16；回答并发：16
- 检索：vector `top_k=5`，graph `append` 模式追加最多 2 条邻居，即 5+2
- Graph 参数：`seed_k=0`、`append_k=2`、`expansion_bonus=0.2`
- 回答温度：0；最大输出：512 tokens；超时：180 秒；重试：2 次
- LLM Judge：OpenRouter `openai/gpt-4o-mini`
- 预计总耗时：约 4.25–5 小时，包含两组建库、QA 和 LLM Judge

## 3.执行

1. 校验两份 chunk 文件、38 个 sample、2,090 条 QA、query embedding 缓存及 embedding 服务。
2. 在 GPU 5 启动或复用端口 8015 的 vLLM，检查模型、显存和请求响应。
3. 使用原有 round chunk 建立全新的 HiveMem memory，完成后执行全量 5+2 检索与 QA。
4. 为 round 组运行 LLM Judge，并检查结果文件及调用追踪。
5. 使用 512-balanced chunk 建立另一套全新的 HiveMem memory，完成后执行相同的全量 5+2 检索与 QA。
6. 为 512-balanced 组运行 LLM Judge，并检查结果文件及调用追踪。
7. 汇总两组的回答指标、检索指标、建库规模、调用成本和实际耗时。
8. 每个阶段启动后进行初期监控，之后每 10 分钟检查一次进度、GPU 状态、错误和进程存活情况。

两组不得共用 memory/index，不得让第二组通过 `--resume` 读取第一组的构建产物。WMA checkpoint 检索必须只使用当前 checkpoint 已可见的 session，避免 future leakage。

## 4.完成条件

- 两组均完成 38 个 sample 的建库和全部 2,090 QA。
- 两组均无回答错误、重复或遗漏问题，question ID 与正式 benchmark manifest 一致。
- 每条检索轨迹均保留 vector Top-5，并在存在有效图邻居时追加不超过 2 条结果。
- 两组分别生成 `results.json`、`retrieval_trace.jsonl`、`pipeline_qa.jsonl`、`metrics.json`、`run_manifest.json`、memory 构建产物及调用追踪。
- 两组均完成 LLM Judge，不存在未处理的 `judge_error`。
- 输出目录相互隔离，且 manifest 能追溯各自使用的 chunk 文件及配置。

## 5. Metric

所有结果统一按以下字段及顺序汇总：

| Chunk 模式 | #Chunks | Avg Tokens | #Memories | F1 | EM | Judge | Hit@5 | Cost-MB | Cost-QA | Lat-MB | Lat-QA | 总耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|

- `Hit@5`：只统计保持原顺序的 vector Top-5；追加的最多 2 条 graph 邻居不改变该指标口径。
- `#Memories`：建库后实际生成的 memory item 数量。
- `Cost-MB`、`Lat-MB`：memory 构建阶段的平均成本与平均估算延迟。
- `Cost-QA`、`Lat-QA`：检索及回答阶段合计的平均成本与平均估算延迟。
- 除总体指标外，同时保存按 question category 和 difficulty 分组的结果。

## 6. Outputs 文件保存规范

两组实验使用独立运行目录：

```text
/data/haozhen/Memory-clean/Offline/outputs/WorldMemArena/HiveMem/0907_round/
/data/haozhen/Memory-clean/Offline/outputs/WorldMemArena/HiveMem/0907_512_balanced/
```

每组 memory 保存到对应运行目录的 `memory/`，QA、metric、Judge 和调用追踪保存在同一运行目录下。运行日志统一保存到：

```text
/data/haozhen/Memory-clean/Offline/logs/wma0907/
```

不得覆盖现有 `outputs/WorldMemArena/HiveMem/` 下的历史正式实验。
